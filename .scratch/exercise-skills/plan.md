## Outcome

`/ask-codex:ui` lets the user have Codex operate their own web app in an isolated, network-restricted Chrome, on a disposable copy of the project, and get a report of bugs (reproduced by Claude through the same restricted browser), layout problems and UX suggestions. Codex's shell stays read-only and cannot escalate; Codex and its browser never write to the user's project, and write nothing outside the disposable target and the run's own directories apart from Codex's own state (`CODEX_HOME`, as in every consultation); nothing the exercise starts outlives it unreported (anything not confirmed ended is reported by PID and image) (Codex, the MCP and its Chrome, the app, the guard's and the reproduction's browsers); the user's project, other local services and data are not touched unless the user says so for that exercise — except through the app itself: the app's own development tools (in-browser consoles, open-in-editor endpoints, file serving) are reachable from the allowed origin and are disclosed, not prevented (U8), and in attach mode (U6) the exercise acts on the user's running dev environment by the user's choice. Windows only. Released as the next minor version after 1.3.3.

## Scope and exclusions

In scope: everything in `spec.md` and tickets 01–08 as amended below.

Excluded (spec "Out of Scope" — except its "Targets other than localhost services started from the disposable target", which does not apply to attach mode, I14 — plus): untrusted repositories (U1); platforms other than Windows — the exercise operations refuse elsewhere (the measured platform; ADR 0005's Linux support covers consultations only); apps that need Docker or other out-of-tree processes (effects outside the job are listed as residual); blocking Codex's shell from other localhost services (P8c, README only); an OS-level sandbox for the browser or the app; DNS prefetch (README: not verified).

- **I1 Target root.** The request names a root the skill marks user-confirmed; the script additionally requires: absolute, existing, a directory and not a reparse point; on a local fixed drive (not UNC, not removable/network); not inside a cloud-sync folder (OneDrive and the other sync roots the script can detect from the environment and known folders); not inside the project and not containing it; no ancestor of the target directory holds `.git` or `.codex`. The target is a new directory created with exclusive create; any existing path is refused. The target record (path, volume serial + file ID of target and root) is written in the exercise's run directory under the scratch base before copying starts, never in the project.
- **I2 Copy.** Every entry is examined with `lstat`; any reparse point (every tag, cloud placeholders included) is neither followed nor recreated — it is skipped and listed. Never copied: VCS metadata in any case and depth (`.git` directory or file, `.hg`, `.svn`, `.jj`), `.codex`, `.claude`, dependency directories (`node_modules`, `.venv`, `venv`, `__pycache__`, `.pnpm-store`, plus names the request adds), `.env*` and secret-pattern files (`*.pem`, `*.key`, `*.pfx`, `*.p12`, `id_*`, `credentials*`) except files the request names explicitly (U2). Only main data streams are copied; alternate data streams are skipped and listed (U11). Limits on entry count and total size; reserved names, over-long paths, names designating a stream and copy errors fail cleanly and remove the partial target. Postconditions: no reparse point inside the target after the copy; after the install command, no reparse point inside the target resolves outside it (else stop).
- **I3 Removal.** Applies to the target and to each recorded sibling MCP `TEMP` directory (I5). The path comes only from the record; the target's and root's identities must match; the target must not be a reparse point; removal never follows a reparse point inside it; read-only files are deleted with the ignore-read-only disposition, never `chmod`; removal happens only after every recorded process of the exercise is confirmed ended (I8, I15; an attached owner in attach mode is never such a process) — otherwise the target is kept and its location reported.
- **I4 Command line.** As `spec.md` "Command line" with `-C <target>`; the constants (read-only, ephemeral, apps off, child agents and `multi_agent_v2` off, `approval_policy="never"`, `approvals_reviewer="user"`, `--ignore-rules`) are not part of overrides or the prepared summary; every other MCP server is disabled whatever the user's policy or allowlist; the MCP listing, definition-file scan and the Codex process all use the target as cwd/project. `ask`, `review`, `discuss` command lines equal the literal baseline from `1ca7a0f`.
- **I5 Browser server definition.** Name `cdt_<nonce>` (fresh per run). Command: absolute `node` path; argument 0 the absolute entry script of chrome-devtools-mcp 1.10.1 installed by the script with `npm install --ignore-scripts` into a script-owned user-level directory and verified before every use against a committed manifest of the installed files' SHA-256 hashes (any difference refuses). `cwd`: an empty directory owned by the run, not inside the MCP's `TEMP`, the evidence directory or the target (so a relative path never resolves into an allowed root). `env`: exactly `CHROME_DEVTOOLS_MCP_NO_CONFIG_DISCOVERY="1"`, `CHROME_DEVTOOLS_MCP_NO_USAGE_STATISTICS="1"`, `NODE_OPTIONS=""`, `TEMP` and `TMP` = a run-owned temporary directory (A1); `env_vars` empty. That directory (R4-1) is dedicated, newly created with exclusive create and empty at start, a sibling of the target under the confirmed root (same volume as the target), recorded in the target record and removed with the target under I3's rules; it is never, and never an ancestor of, the run directory, the target record, stop/signal files, Codex's output files, `plan.json`, the guard cache, the evidence directory or the target. The guard and each repro call get their own directory under the same rule. The record entry for each such directory is written (by atomic replace of the record) before the directory is created, and holds its volume serial + file ID once created. Arguments exactly: `--isolated`, `--headless` unless headed, `--no-javascript-evaluation`, `--no-usage-statistics`, `--no-performance-crux`, `--redactNetworkHeaders`, `--filesystemRoot=<target>/evidence`, `--viewport`, one `--allowedUrlPattern` per app host:port, `--proxyServer=http://127.0.0.1:<owned proxy port>`, `--chromeArg=--proxy-bypass-list=<-loopback>;<each app host:port>`, `--chromeArg=--force-webrtc-ip-handling-policy=disable_non_proxied_udp`; never `--config`, `--browserUrl`, `--wsEndpoint`, `--autoConnect`, `--userDataDir`, `--acceptInsecureCerts`, `--allowUnrestrictedPaths`, `--slim`, any `--category*` or `--experimental*`. `startup_timeout_sec` = 90. `enabled_tools` = the spec's literal list; `tools.<tool>.approval_mode="approve"` for exactly those tools and no other `tools.*` key (B1), and `default_tools_approval_mode="prompt"` (A4); these approval keys are exec constants generated from the same literal list, never in overrides, the prepared summary or `plan.json`, never on `ask`/`review`/`discuss` (A5). The owned proxy port: a loopback listener that accepts and closes every connection, held for as long as a browser of this definition may run (the supervisor for the exercise, the guard and repro processes for theirs). One function produces this definition from a template for the exercise, the guard and the reproduction.
- **I6 MCP guard.** With the exercise overrides and the target as cwd: `codex mcp list --json` shows exactly one enabled server, the nonce-named one; `codex mcp get <name> --json` shows `command`, `args`, `env`, `env_vars`, `cwd`, `enabled_tools`, `startup_timeout_sec` equal to I5's instantiation literally and `disabled_tools` empty or null; the server's default tool approval mode, where `codex mcp get` prints it, is `prompt`; otherwise abort before Codex. `tools.*.approval_mode` is not exposed by either listing (0.159.3): covered by the nonce (no lower layer can name the server in advance) and by offline argv tests; stated as residual.

- **I8 Supervisor and processes.** `app-start` launches one supervisor process per exercise (started with breakaway from the caller's job where permitted, otherwise `app-start` runs as a background execution like `run`) that creates an app Job Object with an unguessable name (`ERROR_ALREADY_EXISTS` refuses; kill-on-close, breakaway not allowed, active-process accounting) and holds its only long-lived handle; the supervisor is not a member of that job.
