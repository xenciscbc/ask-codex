# 02 — An exercise runs through the script on a disposable target (stub Codex)

**What to build:** a UI exercise request goes all the way through prepare → run → wait → collect with the Codex stub: the disposable target is created, Codex is started on it with the exercise command line and exactly one MCP server (the pinned, restricted chrome-devtools-mcp), the reply is classified against a new UI exercise reply schema, and the target is removed after a normal finish or a failure. `ask`, `review` and `discuss` behave exactly as before. This slice also settles how the browser server is launched so that the `<-loopback>` bypass entry reaches Chrome literally (P7: `cmd /c` treats `<` and `>` as redirection); the browser guard (03) proves it live (spec: "Request fields", "Command line", "Browser server definition", "Tool allowlist", "MCP guard", "Reply schema"; user stories 3–6, 9–10, 28–38, 44; ADR 0003, 0005, 0008, 0009, 0010).

**Blocked by:** 01 — Disposable target: create a copy, remove only what was created.

**Status:** ready-for-agent

**Plan:** acceptance amended by `../plan.md` rev 5.1, claim C2 (invariants listed there).

Security-critical (it defines what Codex and its browser can reach): needs a security review and an approved plan before any change.

- [ ] An exercise request (interaction `exercise`, kind `ui`) carries the confirmed target root, the app's host:ports, the headed flag, the scope text and one model; validation refuses before any Codex command: two models, an existing target, an unconfirmed root, no ports, a host that is not loopback, an invalid port.
- [ ] The prepared summary names the interaction, the target root, the ports, headless or headed, and the model.
- [ ] Codex's working directory (`-C`) is the created target and never the project (asserted on the stub's recorded command line).
- [ ] The exercise command line carries every constant: read-only sandbox, ephemeral, apps off, child agents and `multi_agent_v2` off, `approval_policy="never"`, `approvals_reviewer="user"`, `--ignore-rules`; the constants are not part of the overrides or the prepared summary.
- [ ] Every other MCP server is disabled as in a consultation; the browser server is defined with the pinned version and the arguments the spec lists: isolated profile, headless unless headed, no JavaScript evaluation, usage statistics and CrUX off, one allowlist pattern per app host:port, a proxy at a closed local port, a bypass list of exactly `<-loopback>` plus each app host:port, the WebRTC policy, config discovery and usage statistics off by environment, a raised startup timeout.
- [ ] `enabled_tools` is exactly the spec's list; `upload_file`, `take_heapsnapshot` and `performance_*` are absent; the test compares against a literal list, never one generated by the new code.
- [ ] The launch passes `<` and `>` literally (offline: the recorded browser server definition, once decoded the way the launcher decodes it, contains `<-loopback>` unchanged).
- [ ] The MCP guard aborts the exercise before Codex starts unless the browser server is the only enabled server.
- [ ] A UI exercise reply schema is selectable like the discussion schema: claims with `category` (bug, layout, ux), `statement`, `steps`, `expected`, `actual`, `viewport`, `evidence`, `confidence`, `in_scope`; `out_of_scope` observations; `coverage`. Closed objects, all keys required, nullable as `[<type>, null]` (offline structure test). A valid stub reply classifies as structured, a malformed one as unstructured, neither raises.
- [ ] After collect, and after a failed or launch-failed run, the target is gone and the run directory is removed.
- [ ] For `ask`, `review` and `discuss` requests the Codex command line, normalised as in the existing baseline test, equals a literal list captured from `1ca7a0f`.
- [ ] All existing offline harness tests pass (named pre-existing failures excepted, as in earlier tickets).
