# 01 — Script selects the discussion reply schema; stub answers per round

**What to build:** a consultation request can ask for the discussion reply schema, and such a run goes all the way through prepare → run → wait → collect: Codex gets the discussion schema, the reply is classified against it, and the run is cleaned up — while every existing `ask` and `review` consultation behaves exactly as before. The test stub can give a different reply on each call and records each call's prompt and command line at a fixed, numbered location, so later tickets can grade round by round. Prefactor for the `discuss` skill (Plan slice S1; spec: "Discussion reply schema", "Testing Decisions — Seam 1").

**Blocked by:** None — can start immediately.

**Status:** ready-for-agent

- [ ] A request with `reply_schema` absent or `consultation` uses the consultation schema; `discussion` uses the discussion schema; any other value, and `discussion` with two models, is refused before any Codex command.
- [ ] The prepared summary names the reply schema.
- [ ] The discussion schema follows the spec's type shape and structural rules (every object node closed, all keys required, nullable `[<type>, null]`, `stance` enum includes `null`, three booleans typed boolean), checked by an offline structure test.
- [ ] The reply classifier handles booleans: a complete valid discussion reply classifies as structured; the same reply with a boolean given as the string `"true"` classifies as unstructured; neither raises. Existing consultation fixtures classify as before.
- [ ] For a request without `reply_schema` and for one with `reply_schema: "consultation"`, the Codex command line, with run directory, project path and skill directory normalised to placeholders, equals a literal expected list captured from baseline `6266c3e` (comment names the source; never generated by the new code). Changing any flag, its order or the schema basename fails the test.
- [ ] A discussion request run through prepare → run → wait → collect with a valid stub reply ends collected, state completed, format structured, run directory removed.
- [ ] Stub: a two-entry reply sequence over two calls yields the first and second prompt in order in the numbered per-call prompt records, each numbered command-line record holds that call's schema path, and each reply follows its sequence entry. Existing single-call, per-model and call-log records are unchanged for scenarios without a sequence.
